# Hosted demo deployment

FoodFlow has four Next.js web roles: Admin, Restaurant, Customer and Driver. The current user-approved free demo uses a Render Docker NestJS API with an explicitly enabled embedded Postgres outbox worker, Supabase PostgreSQL/PostGIS/Realtime/Storage and TLS Redis. Four frontends remain on Vercel. The API does not run a Socket.IO server in managed mode.

The API is [foodflow-api-3td0.onrender.com](https://foodflow-api-3td0.onrender.com/api/readyz). Web surfaces: [Customer](https://foodflow-customer.vercel.app), [Driver](https://foodflow-driver.vercel.app), [Admin](https://foodflow-admin-two.vercel.app), [Restaurant](https://foodflow-restaurant-ochre.vercel.app). Deployment state and browser verification remain separate checks.

Render Free sleeps after 15 minutes without inbound traffic. The user accepted that durable jobs pause during sleep and resume on HTTP wake. `FOODFLOW_EMBEDDED_WORKER=true` is API-only, default-off, requires the Postgres provider and rejects Vercel Functions. It reuses one dependency graph, avoids overlapping drains and waits before disconnecting Prisma/Redis. One-second polling, 15-second retries and 30-second offers apply while running; sleep/restart can delay execution. This is a portfolio demo with no continuous availability guarantee. The existing standalone worker remains available. Optional RAG is disabled.

`backend/vercel.json` and `backend/vercel.worker.json` retain the alternative Vercel topology. The worker static build succeeded but Daemon activation returned403; it is not a running Vercel worker. No paid upgrade or artificial keepalive is configured.

`DB_SSL_CA` supplies the public database CA certificate. The Prisma runtime writes that public certificate to a hash-named temporary file and enables strict certificate verification. Redis uses `rediss://`. Keep database passwords, Redis credentials, service-role credentials and realtime signing keys in server-only encrypted environment variables.

Run the reviewed [managed bootstrap](managed-bootstrap.md) before rollout. Historical migration bytes are retained. Provider-owned operations are completed through verified, hash-pinned compatibility checkpoints; forward migrations confine application tables and retire the obsolete browser outbox policy. Browser application data goes through the Nest API; private Broadcast authorization remains in `realtime.messages`.

A new, empty demo database may be initialized through `prisma/seed.ts` with `NODE_ENV=production`, `FOODFLOW_EMPTY_DEMO_BOOTSTRAP=CREATE_EMPTY_DEMO_ONLY` and a generated private `FOODFLOW_DEMO_PASSWORD` of at least 24 characters. This path refuses an existing user database. It deliberately inserts sample restaurants, customers, drivers, orders and support tickets. They are demonstration fixtures. Never use it to migrate an existing service or real customer data. Demo credentials are kept in an ignored local file and are not published in source.
